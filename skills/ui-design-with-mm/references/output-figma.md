# Output: Figma via MCP

Read when the selected target is Figma via MCP. Shared rules for all targets are in [output targets](output-targets.md).

Use the connected tool's actual documented capabilities and required host guidance. Do not assume that an MCP connection can create variables, components, or prototype interactions merely because it can read designs. If a required capability is absent, disclose the incomplete deliverable and ask for a capable connection or an explicit target change. A token table or code snippet is not completed Figma work.

1. Confirm the intended file and page. Read the project-scoped context record for an existing product, then reconcile it with the live file. **Before designing any screen or element**, inspect that file and its libraries for existing collections, styles, components, variants, icons, and illustrations. Reuse every fitting component, including in scoped edits. Show any gap and obtain approval through the choice layer before creating a reusable component or proper variant. Never detach or restyle an instance to fake a variant.
   When a live page or existing product is the source, follow [source fidelity](source-fidelity.md): record the source inventory before designing, keep the captures at each target width until the comparison is finished, and complete the source diff before handoff. A capture that was removed before comparison cannot support a fidelity claim; report unavailable source measurements as unverified.
2. State naming and locations before writing. For a new file without conventions, use pages `Foundations`, `Components`, and `Screens`; variable collections `Primitives` and `Semantic`; and component groups `Atoms`, `Molecules`, `Organisms`, and `Templates` on the Components page, with pages built on the Screens page as instances of templates. Preserve existing conventions for edits. Collections belong to the file; a Foundations page documents them but does not contain the collections themselves.
3. Create primitives and semantic aliases through supported variable types. Use styles for composite typography or properties not supported as variables, and document how those styles map to the two-tier definitions. Do not claim unsupported bindings exist.
4. Build approved missing components and the scoped screens using semantic bindings. Every component you create uses Auto Layout, and every component set is laid out with Auto Layout and at least 24px between variants, as set out in [component library](component-library.md). Use Auto Layout for content groups too; use Hug/Fill sizing, text auto-height, and constraints so content reflows as frames resize. Every content-bearing element must define its intermediate-width behavior: text and labels wrap, icon-label pairs reflow, typography and icons use approved size steps, controls stack or reflow, and content grows intrinsically. Do not shrink below readable type or touch-target minimums, or use fixed heights to hide overflow. Apply fluid width with a max-width where line length, form usability, card density, document readability, dialog composition, or header hierarchy would suffer on a very wide frame. Center capped regions and let them grow to the cap; do not cap full-bleed media, backgrounds, tables, or workspace canvases without evidence. Reserve fixed dimensions for elements whose source or behavior requires them, and state that reason. Where the layout changes at a breakpoint, build the section or region as a component set with a breakpoint property so one instance switches layout; Auto Layout alone does not switch layouts at breakpoints, and separate frames per breakpoint are only labelled snapshots of those instances. Set minimum and maximum widths on containers that must stop shrinking or growing. Define and build the applicable component states before handoff: resting, hover, focus-visible, pressed, selected, disabled, loading, success, error, warning, empty, expanded/collapsed, and pattern-specific states. Use reusable variants and properties rather than one-off state styling, and verify supported prototype transitions. Use the brand's icon components and illustration assets from the library. If either style is absent, document the approved choice described in [component library](component-library.md) before creating or using it. Keep one icon style, one illustration style, and marked illustration placeholders. Do not substitute loose vectors or ad hoc artwork for missing library assets. For a prototype, connect the agreed flow and relevant states with supported interactions. Keep planned copy and placeholders identifiable. Bind every value: each text node uses a text style or font variables, and each fill, stroke, corner radius, spacing, padding, and effect uses a variable or style. A value that is only selected or typed in, and not attached to a variable or style, is unbound and is a defect. When you create a page, set its canvas background to the user's stored canvas preference, if one exists, and read it back; never change an existing page's background unless asked. The canvas is a viewing setting, not a design decision: do not bind it to design tokens, and judge frames on their own backgrounds. Build level by level (atoms, molecules, organisms, templates, pages, as set out in [token structure](token-structure.md)), and run the binding audit on each level, reaching zero unbound values, before starting the next.
5. Read back created/changed collections, variables, aliases, bindings, styles, nodes, and state variants. For every component and component set created, confirm that Auto Layout is on and that the space between variants is at least 24px. Confirm the intended file, resolved values, actual component references, reusable icons, and illustration assets. Inspect rendered screens and the relevant prototype behavior, including key state transitions and recovery paths. Resize the frames continuously or at representative widths: narrow, just before and after each breakpoint, and wide. Confirm titles, body text, metadata, evidence, labels, icon-label pairs, buttons, controls, and navigation wrap or recompose without clipping, overlap, accidental truncation, unreadable type, or horizontal overflow. Confirm typography and icons use approved breakpoint sizes, content-bearing regions use intrinsic height, touch targets remain reachable, and capped regions remain centered with readable line lengths at very wide widths. Confirm that max-width rules do not create overflow at narrow widths. Separate fixed viewport presentation frames from components/layouts that are actually resize-responsive. Do not report responsive behavior or state coverage as passed based only on having desktop and mobile frames. **Binding-coverage audit:** across every component and screen you created or changed, count the text nodes without a text style or font variables, and the fills, strokes, radii, spacing values, and effects without a variable or style. Report the counts. The target is zero; list each exception with its reason. Do not report binding as passed from a sample. Run [the Figma audit script](../scripts/figma-audit.js) through the plugin-API tool where the connection allows it. It passed a self-test on a scratch file, but on a new connection first create a deliberately unbound test node and confirm the script flags it before trusting a zero; if the script errors or misses the test node, audit each node by hand and say so. Also read back the composition of each level and report any loose frame, detached instance, or hand-built section.
6. **Verify visibility and discoverability:** inspect the variables interface when possible. If UI inspection is unavailable, verify existence by readback, report that visual visibility remains unverified, and provide the exact collection names and route to find them. Do not claim a visual check you did not perform.
7. Deliver the file/page or node links and a short location map for collections, styles, components, icons, illustrations, and screens. Mark approved new components and variants as new. State what was checked and what remains unverified. If readback fails, report creation as unconfirmed and resolve it before calling the Figma deliverable complete.

Variable naming/location plus readback are always required. Name pages, frames, components, properties, layers, styles and flows as set out in [Figma naming](figma-naming.md). The same discoverability discipline applies to every Figma artifact, not only color tokens. Do not publish a library or make a file public merely to deliver a design.


## Lean runs and hosts that meter usage

Where the host meters usage, such as credits or paid steps, or when the user asks for a lean run:

- Discover once. Search the library, styles and variables once per run, record the component keys and variable names in the plan or on a Notes frame, and reuse them. Do not search again for the same asset for each screen or state.
- Work in stages and stop at each: first a plan with nothing built; then any new components, built once; then one screen or state at a time. Run the delivery gate for the stage before the next one.
- Show a state as the changed region plus enough surrounding context, with one full-page reference. Build full-page states only when asked, because each full page repeats the shell.
- Reuse before creating. Never rebuild a component per screen.
- Verify once per stage: audit only the nodes touched and take one screenshot after composition.
- State the scope and an estimate before building. If the run must stop for budget, say so and list the remaining work. A budget stop is declared, never a pass.

## Figma host notes

- On the Figma MCP connection, loadAllPagesAsync, setPluginData and createImageAsync are not supported, and figma.notify throws an error. Page context resets to the first page on every call: switch once per call with setCurrentPageAsync, and use one call per page for multi-page work.
- Images cannot be fetched by URL through the plugin API. For a web source, capture the page with the host's capture tool and copy image hashes onto the image slots, or use the host's upload tool. Otherwise list the images as unverified.
- Load the host's own Figma skills before writing, for example figma-use and figma-generate-design. They supply the API rules and are subordinate to this method.
