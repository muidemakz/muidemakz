# Supporting guidance

Read when a stage could benefit from a specialist skill that the host offers. This method stays primary. Supporting guidance informs a stage; it never replaces a gate, a reference, or an approval, and it never supplies the evidence for a decision.

## Rules

- Use supporting guidance only when it is available in the host and relevant to the stage. Availability varies by host and install; check before relying on it, and carry on with this method when it is absent.
- Read the supporting guidance before using it. Do not rely on its name or one-line description.
- When it conflicts with this method, this method wins. Record the conflict in the delivery note and send any real disagreement through the choice layer.
- Name each supporting skill you actually used in the run receipt, the checkpoint, and the delivery note. Do not name one you did not read.
- Do not copy its text into this skill, the record, or a deliverable. Use its ideas, in your own words, with attribution where the content is reproduced.
- Preferences and supporting guidance cannot waive accessibility, source fidelity, or an approval gate.

## Where each kind helps

| Stage | Kind of guidance | Examples when available | Limit |
| --- | --- | --- | --- |
| Motion and interaction | Deciding whether and how to animate, naming an effect | `animate`, `animation-vocabulary` | Motion still needs a stated purpose and reduced-motion behavior; the slop checklist's motion pattern still applies. |
| Polish and feel | Details that make an interface feel considered | `emil-design-eng`, `apple-design` | Taste guidance is not brand evidence. A polish choice needs a source or an approved direction. |
| Token and component architecture | Naming and structuring tokens and components | `design-system` | This method keeps exactly two token tiers, primitive and semantic, as in [token structure](token-structure.md). Where guidance proposes a third tier, keep two. |
| Greenfield code aesthetics | Building an expressive interface when no brand or source exists | `frontend-design` | Do not use it for an existing product, a named brand, or anything that must match a source: it favors unexpected choices, which conflict with [source fidelity](source-fidelity.md). Use it only after the visual direction gate. |
| Review and critique | A second pass on a finished interface | `impeccable` | Findings are leads to verify against this method's checks, not a grade. |
| Figma | The host's own rules for writing to Figma | the Figma MCP's required skills | Required before writing through that connection, as in [Figma via MCP](output-figma.md). |

The examples are skills a host may offer. Their presence here is not a claim about their contents or licences.
